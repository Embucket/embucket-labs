# Архитектура Self Service UI на Lambda

## Обзор

Embucket - это OSS (Open Source Software) проект, который можно развернуть самостоятельно (self deployment). Self service модель позволяет использовать Embucket UI без ручной настройки инфраструктуры. Клиент получает URL Lambda функции, открывает его в браузере, и система автоматически запускается.

---

## Варианты Entry Points для клиента

Клиент может начать использовать Embucket несколькими способами в зависимости от его потребностей и уровня технической экспертизы.

### 1. Готовый Lambda Function URL (Самый простой)

**Для кого:** Для быстрого старта и тестирования

**Процесс:**
```
Клиент → Получает готовый URL из документации/GitHub → Открывает в браузере → Использует
```

**Где получить URL:**
- README проекта на GitHub
- Документация по быстрому старту
- Примеры в репозитории
- Email от команды (для beta-тестеров)

**Формат URL:**
```
https://{lambda-id}.lambda-url.{region}.on.aws/
```

**Преимущества:**
- ✅ Мгновенный старт — не нужно ничего настраивать
- ✅ Идеально для тестирования и демо
- ✅ Нет необходимости в AWS аккаунте

**Ограничения:**
- ⚠️ Использует общие ресурсы (S3 bucket, Postgres)
- ⚠️ Может быть ограничен по функциональности
- ⚠️ Не подходит для production данных

---

### 2. Автоматическое создание через CLI/Web интерфейс

**Для кого:** Для пользователей, которые хотят свой собственный инстанс

**Процесс:**
```
Клиент → Указывает S3 bucket → CLI/Web создает Lambda → Выдает Function URL
```

**Пример использования CLI:**
```bash
# Установка CLI
npm install -g @embucket/cli

# Создание Lambda инстанса
embucket deploy \
  --s3-bucket my-data-bucket \
  --region us-east-1 \
  --output url
```

**Пример использования Web интерфейса:**
1. Открыть `https://embucket.io/deploy`
2. Ввести AWS credentials (или использовать OAuth)
3. Выбрать S3 bucket
4. Нажать "Deploy"
5. Получить Function URL

**Что создается автоматически:**
- UI Lambda функция с Function URL
- Query Lambda функция
- Postgres Aurora Serverless (если не существует)
- Необходимые IAM роли и политики
- S3 bucket для результатов (опционально)

**Преимущества:**
- ✅ Полный контроль над данными
- ✅ Изолированный инстанс
- ✅ Автоматическая настройка инфраструктуры
- ✅ Подходит для production

**Требования:**
- AWS аккаунт
- AWS credentials с необходимыми правами
- S3 bucket с данными (Iceberg tables)

- ✅ Интеграция с CI/CD

## Поток работы

После того как клиент выбрал подходящий entry point (см. раздел "Варианты Entry Points для клиента"), начинается следующий поток работы:

### 1. Клиент получает URL Lambda

Клиент получает Function URL одним из способов, описанных выше. Формат URL:
```
https://{lambda-id}.lambda-url.{region}.on.aws/
```

---

### 2. Клиент открывает URL → Lambda запускается

```
Браузер → Lambda Function URL → Lambda запускается
```

**Что происходит:**
- Lambda находится в "холодном" состоянии (остановлена)
- AWS Lambda Runtime запускает Node.js runtime
- Загружается Express сервер
- **Время:** 0.1-0.5 секунды (холодный старт)

**После первого запроса:**
- Lambda остается "теплой" 5-15 минут
- Последующие запросы обрабатываются мгновенно

---

### 3. Node.js сервер отдает React UI

```
Lambda → Express → Отдает index.html из static/ → React UI загружается
```

**Структура запроса:**
```
GET / → Express.static('static/') → index.html
GET /assets/* → Express.static('static/assets/') → JS/CSS файлы
GET /favicon.ico → Express.static('static/') → favicon
```

**Что происходит:**
- Express сервер отдает статические файлы из папки `static/`
- `index.html` загружается в браузер
- React приложение инициализируется
- UI делает запросы к `/ui/api/*` endpoints

---

### 4. React UI делает запросы к Node.js серверу

```
React App → /ui/api/databases → Node.js Lambda
React App → /ui/api/tables → Node.js Lambda
React App → /ui/api/queries → Node.js Lambda
```

**Примеры запросов:**

**Метаданные:**
```javascript
// Получить список databases
GET /ui/api/databases
→ Node.js Lambda → Postgres → Возвращает список

// Получить список tables
GET /ui/api/databases/{db}/schemas/{schema}/tables
→ Node.js Lambda → Postgres → Возвращает список
```

**SQL запросы:**
```javascript
// Выполнить SQL запрос
POST /ui/api/queries/execute
Body: { sql: "SELECT * FROM sales WHERE revenue > 1000" }
→ Node.js Lambda → Query Lambda (Rust) → Возвращает результат
```

---

### 5. Node.js сервер обращается в Postgres (для метаданных)

```
Node.js Lambda → Postgres (Aurora Serverless)
```

**Что хранится в Postgres:**

**Метаданные:**
- Databases, schemas, tables, columns
- Volumes (storage configurations)
- Query history, results metadata

**UI состояние:**
- Worksheets, saved queries
- User preferences, workspace settings

**Пользователи и сессии:**
- Auth tokens, user sessions

**Примеры запросов:**
```sql
-- Получить databases
SELECT * FROM databases;

-- Получить tables для schema
SELECT * FROM tables 
WHERE database = $1 
  AND schema = $2;

-- Сохранить query history
INSERT INTO query_history (sql, status, duration)
VALUES ($1, $2, $3);
```

**Почему Postgres, а не только S3:**
- S3 медленный для частых запросов (latency 100-200ms)
- Нужны транзакции и ACID для консистентности
- Нужны индексы для быстрого поиска
- UI нужен быстрый доступ к метаданным

---

### 6. SQL запросы → Query Lambda (Rust)

```
React App → POST /ui/api/queries/execute
  ↓
Node.js Lambda → POST Query Lambda (Rust)
  ↓
Query Lambda → DataFusion → S3 (Iceberg tables)
  ↓
Query Lambda → Возвращает результат → Node.js Lambda → React App
```

**Почему отдельная Lambda для SQL:**
- **Разделение ответственности:** UI Lambda для UI, Query Lambda для SQL
- **Производительность:** Rust + DataFusion быстрее для SQL execution
- **Масштабирование:** Query Lambda масштабируется независимо
- **Изоляция:** Долгие SQL запросы не блокируют UI

**Пример потока:**
```javascript
// Node.js Lambda handler
router.post('/ui/api/queries/execute', async (req, res) => {
  const { sql, database, schema } = req.body;
  
  // Сохранить query в history (Postgres)
  const insertResult = await db.query(
    'INSERT INTO query_history (sql, status) VALUES ($1, $2) RETURNING id',
    [sql, 'RUNNING']
  );
  const queryId = insertResult.rows[0].id;
  
  // Вызвать Query Lambda (Rust)
  const queryLambdaUrl = process.env.QUERY_LAMBDA_URL;
  const response = await fetch(queryLambdaUrl, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      sql,
      database,
      schema
    })
  });
  
  const result = await response.json();
  
  // Обновить query history
  await db.query(
    'UPDATE query_history SET status = $1, result_id = $2 WHERE id = $3',
    [result.status, result.id, queryId]
  );
  
  res.json(result);
});
```

## Компоненты системы

### UI Lambda (Node.js)

**Ответственность:**
- Отдача React UI статики
- Обработка UI API endpoints (`/ui/api/*`)
- Работа с метаданными (Postgres)
- Маршрутизация SQL запросов к Query Lambda

**Технологии:**
- Node.js 20.x runtime
- Express.js сервер
- `serverless-http` для адаптации к Lambda
- `pg` для работы с Postgres
- JWT для авторизации

**Размер:** 5-50MB  
**Старт:** 0.1-0.5 сек  
**Память:** 128-512MB

---

### Query Lambda (Rust)

**Ответственность:**
- Выполнение SQL запросов через DataFusion
- Работа с Iceberg каталогом
- Чтение данных из S3

**Технологии:**
- Rust runtime (Container Image)
- Apache DataFusion
- Apache Iceberg

**Размер:** 500MB-2GB  
**Старт:** 5-15 сек  
**Память:** 1-4GB

---

### Postgres (Aurora Serverless v2)

**Ответственность:**
- Хранение метаданных (databases, schemas, tables)
- Хранение query history
- Хранение UI состояния (worksheets, saved queries)
- Хранение пользователей и сессий

**Особенности:**
- Scale-to-zero автоматически
- Row Level Security (RLS) для безопасности (опционально)

---

### S3 (Iceberg Tables)

**Ответственность:**
- Хранение данных таблиц
- Хранение метаданных Iceberg (manifest files)
- Хранение партиций

## Безопасность

### Function URL

**Вариант 1: AWS_IAM**
- Требует AWS credentials
- Максимальная безопасность
- Нужны модифицированные клиенты

**Вариант 2: NONE (Public)**
- Доступен всем
- Используется JWT токены для авторизации
- Rotating secrets для совместимости

### Авторизация

**JWT токены:**
- Клиент логинится → получает JWT токен
- Все запросы содержат `Authorization: Bearer {token}`
- Lambda валидирует токен и извлекает информацию о пользователе

## Масштабирование

### UI Lambda

- **Автоматическое:** AWS Lambda автоматически создает новые инстансы при нагрузке
- **Scale-to-zero:** Lambda останавливается когда не используется
- **Лимиты:** До 1000 concurrent executions (по умолчанию)

### Query Lambda

- **Автоматическое:** Отдельное масштабирование от UI Lambda
- **По запросам:** Каждый SQL запрос может запустить новую Lambda

### Postgres (Aurora Serverless v2)

- **Автоматическое:** Масштабируется от 0.5 ACU до 16 ACU
- **Scale-to-zero:** Останавливается при отсутствии запросов

## Self Service flow

### Для клиента:

1. **Выбирает entry point** (см. раздел "Варианты Entry Points для клиента")
2. **Получает URL** (в зависимости от выбранного варианта)
3. **Открывает URL в браузере**
4. **Логинится** (если требуется)
5. **Использует UI** — все работает автоматически

### Для системы:

1. **Lambda запускается** при первом запросе
2. **UI загружается** из статики
3. **API запросы обрабатываются** Node.js сервером
4. **Метаданные читаются** из Postgres
5. **SQL запросы выполняются** через Query Lambda
6. **Lambda останавливается** через 5-15 минут бездействия

## Преимущества Self Service модели

✅ **Нет платы за idle:** Lambda останавливается когда не используется  
✅ **Автоматическое масштабирование:** AWS управляет всем  
✅ **Нет DevOps:** Клиент не управляет инфраструктурой  
✅ **Быстрый старт:** 0.1-0.5 сек для UI Lambda  
✅ **Низкая стоимость:** Плата только за использование  
✅ **Простота:** Один URL для всего (UI + API)

## Минусы и потенциальные челленджи

### Холодный старт

**Проблема:**
- UI Lambda: 0.1-0.5 сек (приемлемо)
- Query Lambda: 5-15 сек (может быть проблемой для пользователей)

**Влияние:**
- Первый SQL запрос после простоя может занять 15+ секунд
- Пользователь видит долгую загрузку без обратной связи

**Решения:**
- Provisioned Concurrency для Query Lambda (дополнительная стоимость)
- Keep-alive механизм для поддержания Lambda в "теплом" состоянии
- Предупреждение пользователя о возможной задержке первого запроса
- Pre-warming Lambda перед критическими операциями

---

### Лимиты Lambda

**Timeout:**
- Максимальное время выполнения: 15 минут (Lambda)
- Долгие SQL запросы могут превысить лимит

**Размер ответа:**
- Максимальный размер ответа: 6MB (Lambda Function URL)
- Большие результаты запросов могут не поместиться

**Concurrent executions:**
- По умолчанию: 1000 одновременных выполнений
- Может быть недостаточно для высоконагруженных сценариев

**Решения:**
- Асинхронное выполнение долгих запросов (SQS + polling)
- Пагинация результатов больших запросов
- Streaming результатов через WebSocket или Server-Sent Events
- Запрос увеличения лимитов у AWS Support

---

### Стоимость при высокой нагрузке

**Проблема:**
- При постоянной нагрузке Lambda может быть дороже традиционных серверов
- Postgres Aurora Serverless может быть дороже обычного RDS при постоянной нагрузке
- Query Lambda с большим объемом памяти (2-4GB) дорогая

**Примеры:**
- 1000 запросов/сек × 200ms × 512MB = ~$88/месяц только за Lambda
- Postgres 2 ACU постоянно = ~$144/месяц
- Query Lambda 100K запросов × 5s × 4GB = ~$133/месяц

**Решения:**
- Мониторинг стоимости и оптимизация
- Использование Provisioned Concurrency только когда необходимо
- Оптимизация размера памяти Lambda
- Переход на ECS/Fargate для постоянной нагрузки

---

### Синхронизация метаданных

**Проблема:**
- Метаданные хранятся в двух местах:
  - Postgres (для быстрого доступа UI)
  - S3/Iceberg (источник истины)
- Риск рассинхронизации между ними

**Сценарии рассинхронизации:**
- Таблицы добавлены напрямую в S3, но не синхронизированы с Postgres
- Удаление таблиц в S3, но они остаются в Postgres
- Изменение схемы таблицы без обновления Postgres

**Решения:**
- Периодическая синхронизация метаданных (cron job)
- Event-driven синхронизация при изменениях в S3
- Lazy loading: загрузка метаданных из Iceberg при первом запросе
- Валидация метаданных перед выполнением запросов

---

### Безопасность и изоляция

**Проблемы:**
- Public Function URL требует надежной авторизации
- JWT токены могут быть скомпрометированы
- Нет встроенной защиты от DDoS атак
- Общие ресурсы (Postgres, S3) требуют правильной изоляции

**Риски:**
- Неавторизованный доступ к данным
- SQL injection через пользовательские запросы
- Rate limiting отсутствует по умолчанию
- CORS настройки могут быть неправильно настроены

**Решения:**
- Использование AWS WAF для защиты Function URL
- Строгая валидация SQL запросов
- Rate limiting на уровне Lambda или API Gateway
- Регулярная ротация JWT секретов
- Audit logging всех операций

---

### Отладка и мониторинг

**Проблемы:**
- Распределенная система сложнее отлаживать
- Логи разбросаны по разным сервисам (CloudWatch, Postgres, S3)
- Нет единой точки мониторинга
- Сложно отследить полный путь запроса через несколько Lambda

**Челленджи:**
- Отладка проблем производительности
- Трассировка ошибок между компонентами
- Мониторинг стоимости в реальном времени
- Алерты при проблемах

**Решения:**
- AWS X-Ray для distributed tracing
- Централизованный logging (CloudWatch Logs Insights)
- Дашборды в CloudWatch или Grafana
- Настройка алертов на метрики (latency, errors, cost)

---

### Зависимость от AWS

**Проблемы:**
- Vendor lock-in в AWS экосистему
- Сложность миграции на другие облака
- Зависимость от доступности AWS сервисов
- Региональные ограничения (некоторые сервисы доступны не везде)

**Влияние:**
- Сложность портирования на другие облака
- Риск при изменении AWS политики/цен
- Ограничения по регионам для некоторых клиентов

**Решения:**
- Абстракция над AWS сервисами где возможно
- Поддержка альтернативных deployment вариантов (Docker, K8s)
- Документация по миграции
- Мульти-облачная стратегия для критичных компонентов

---

### Производительность для больших данных

**Проблемы:**
- Query Lambda имеет ограничения по памяти (до 10GB)
- Чтение больших таблиц из S3 может быть медленным
- Нет кэширования результатов запросов
- Параллелизм ограничен concurrent executions

**Ограничения:**
- Очень большие JOIN операции могут не поместиться в память
- Сканирование больших таблиц занимает много времени
- Нет индексов на данных в S3 (только партиционирование)

**Решения:**
- Оптимизация запросов через партиционирование
- Кэширование частых запросов (ElastiCache)
- Streaming обработка больших результатов
- Предупреждения пользователю о долгих запросах

---

### Управление версиями и обновлениями

**Проблемы:**
- Обновление Lambda требует деплоя всех инстансов
- Нет автоматического обновления для self-deployed инстансов
- Риск breaking changes при обновлении
- Разные версии у разных клиентов

**Челленджи:**
- Координация обновлений
- Обратная совместимость API
- Миграция данных при обновлениях
- Поддержка старых версий

**Решения:**
- Semantic versioning
- Feature flags для постепенного rollout
- Миграционные скрипты для данных
- LTS версии для стабильности
- Четкая политика поддержки версий

---

### CORS и статические файлы

**Проблемы:**
- Lambda Function URL требует правильной настройки CORS
- Статические файлы отдаются через Lambda (дополнительная стоимость)
- Нет CDN для статики (медленнее для пользователей далеко от региона)

**Решения:**
- Правильная настройка CORS headers в Express
- Использование CloudFront для статики (опционально)
- Кэширование статических файлов в браузере
- Оптимизация размера статических файлов
